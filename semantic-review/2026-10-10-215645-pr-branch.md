# Village Banking ledger engine — whole-branch review

This branch adds the full 2026 history import pipeline on top of the ledger foundation already on `main`:
a hardening migration (H1, `20261010001700`), two CLI tools (`ledger:import`, `ledger:check`), a workbook
parser, an admin React page, and 16 pgTAP test files. The SQL-side arithmetic stays entirely in Postgres;
the JS side only reads cells and passes them as a JSON bundle. H1 tightened the security posture materially:
`service_role` lost write access to all ten ledger tables, TRUNCATE is blocked on four of them, and four
concurrency bugs were closed.

Watch for: **(1)** `close_month` on the commit path does a plain `SELECT` for `group_id`, checks
`is_admin`, then issues `SELECT … FOR UPDATE`. The locked row has no `if not found` guard; a row that
disappears between the two reads would silently dereference a null `v_p` — **confirmed minor**, FK
constraints make this unreachable today but a future schema change could expose it. **(2)** The
`penalty_not_charged` reason code uses `membership_fee` as its detection threshold rather than
`penalty_per_day`, so it fires only when a workbook minimum coincidentally differs by exactly one
membership fee — **confirmed Important**, suppresses real unexplained differences as `penalty_not_charged`
and makes the test in `12_ledger_diff.sql` pass only because the fixture's two values happen to be equal.
**(3)** `import_history` accepts a `rows: []` empty array for a month, closing it with no member
statements — **confirmed minor**, the JS parser prevents this in practice.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The money maths is locked inside SQL and the closing logic is shared between the live and import paths. The payment-order allocation (excess → penalties → interest → principal) and the ngwee-truncation/remainder logic in `close_figures` are sound. The import's bundle validation is thorough: NaN, out-of-range amounts, missing fields, and cycle-date coherence are all caught before any row is written.

The `close_month` two-read pattern added in H1 (plain read → `is_admin` → `FOR UPDATE`) puts all status checks on the locked row, so the concurrency logic is correct. The gap is that the locked read has no `if not found` guard; the function relies on the pre-lock read having established existence. An FK chain currently makes the row undeletable, but the guard is implicit rather than explicit.

The `import_reset` flag is passed with `local = true` to `set_config`, making it transaction-scoped in Postgres — it resets automatically at commit or rollback. The import wraps everything in one transaction, so the delete window is correctly bounded. The explicit `set_config(…, 'off', true)` that follows the deletes is misleading: it implies a manual reset is needed when the transaction boundary already handles it.

The `penalty_not_charged` heuristic compares a minimum difference against `membership_fee` rather than `penalty_per_day`. In the fixture these two values are both 50 (K50 fee, K1/day penalty × 50 coincidentally matches nothing), which makes the existing test pass while the production group's values differ. Differences that represent a genuine un-applied penalty will be classified `unexplained` instead.

The CLI production guard is robust: `--write` requires `--target`, `--target` must match the actual project ref extracted from the URL, and production is refused unless `--target` names it by ref. The `hostedWithoutRef` check added to `db-cli.mjs` and `db-test.mjs` closes the gap where a hosted non-prod database could be mistaken for local.

Test quality is high. The pgTAP matrix covers anon, outsider, another group's member, a member's own self-service, the admin, and the owner, with explicit cross-group boundary probes. The JS tests run the full import pipeline against a synthetic workbook with a mocked database. The one gap is no test for correcting an import-sourced entry from a closed month, which is the most likely real-world use of `post_correction` in the 2026 cycle.

<summary>Issues (6)</summary>

1. **penalty_not_charged threshold** — `close_diff` uses `membership_fee` as the detection threshold, but the workbook charges `penalty_per_day × days_late`. The code fires only when the workbook's number coincidentally equals exactly one membership fee. In the fixture both values are 50, so the test in `12_ledger_diff.sql` passes without exposing the bug. In production the reason code almost never fires, and real penalty-explained differences land in `unexplained`. Fix: use `penalty_per_day`, or document the heuristic as approximate and name what it actually matches. **Important.**

2. **close_month: no not-found guard after FOR UPDATE** — The commit path's two-read pattern relies on the pre-lock read to establish that the row exists. The `SELECT … FOR UPDATE` has no `if not found then raise` guard. An FK chain currently makes the row undeletable, but if that ever changes, `v_p` is null and every subsequent access silently returns null results rather than raising an error. Add `if not found then raise exception 'period_not_open'` after the locked read. **Minor.**

3. **import_reset GUC: misleading explicit reset** — `set_config(…, 'on', true)` is transaction-local (resets at commit/rollback). The explicit `set_config(…, 'off', true)` that follows implies a manual reset is required, but it is not. A future copy that uses `false` (session-scoped) would leave the flag sticky across connections on a pooler. Add a comment explaining that `true` = transaction-local, no manual reset is needed. **Minor.**

4. **import_history: empty-rows month accepted** — Bundle validation checks that `rows` is an array but not that it has at least one element. An empty-rows month closes with no member statements. The JS workbook parser prevents this in practice (`no member rows under the header`), but the SQL function is callable directly by `postgres` without the JS layer. Add `jsonb_array_length(m -> 'rows') = 0` to the validation block. **Minor.**

5. **workbook_term_differs: upper bound too loose** — `abs(d.difference) <= e.principal_left` allows the code to explain away a K500 minimum gap for any member with K501 still owed. This is a tightening from `1300` (which had no upper bound at all) but is still loose enough to suppress real unexplained minimums for active borrowers. Document as a known approximation or tighten to within one instalment's worth. **Minor.**

6. **No test for post_correction against an imported entry** — No pgTAP test verifies that correcting an import-source entry lands in the open month (not the import's closed month) and that `v_eff` is computed correctly when the original `period_id` is closed. The function is unchanged from `1100`, so this is a coverage gap rather than a regression risk, but it is the most common treasurer action during the first app-managed month. **Minor.**

### penalty_not_charged uses the wrong threshold

In `close_diff` (`1350_ledger_diff_fixes`, also `1300`):

```sql
when abs(d.difference + v_r.membership_fee) < 1 then 'penalty_not_charged'
```

The UI label is "Workbook asked for a charge the app does not raise." The charge the workbook raises that the app does not is a penalty: `penalty_per_day × days_late`. Using `membership_fee` as the threshold means this fires only when the numeric difference happens to equal the membership fee — not a penalty amount.

The test in `12_ledger_diff.sql` uses:

```sql
(tests.id('lg'), tests.lp(1), tests.lm('Fay'), 'next_minimum', 51.02)  -- app 1.02: −50.00
```

The fixture's `membership_fee = 50` and `penalty_per_day = 1`, so the test passes for the wrong reason: 50 equals `membership_fee`, not `penalty_per_day × n` for any plausible n. In production, `penalty_per_day` is K1/day and `membership_fee` is K50; a one-day-late penalty of K1 would not trigger this code, and the difference would land in `unexplained`. **Confirmed. Important.**

### close_month: no not-found guard after FOR UPDATE

H1's commit path:

```sql
select group_id into v_group_id from periods where id = p_period;          -- (A)
if not found then raise …; end if;
if not is_admin(v_group_id) then raise …; end if;
select * into v_p from periods where id = p_period for update;              -- (B)
-- no if not found here
if p_commit and v_p.status = 'closed' then raise …; end if;
```

Between (A) and (B) the row cannot be deleted in practice — `entries`, `loans`, and `loan_instalments` all hold FKs into `periods` — but if any of those FKs were later changed to `ON DELETE CASCADE`, the locked read could return `not found` silently. Every subsequent `v_p.field` access would return null, and guards like `v_p.status = 'planned'` would be silently false rather than raising. One line after (B) fixes this completely. **Confirmed. Minor.**

### import_reset GUC: misleading explicit reset

```sql
perform set_config('ledger.import_reset', 'on', true);   -- 'true' = transaction-local
delete from …;
perform set_config('ledger.import_reset', 'off', true);  -- misleading: not needed
```

The `true` third argument to `set_config` scopes the change to the current transaction. The second call implies a manual reset is required, but the transaction boundary handles it. A developer who later moves the deletes to a subtransaction, or copies this pattern with `false`, would get session-sticky behaviour on a connection pooler. A brief comment — "transaction-local; no manual reset required" — avoids the confusion. **Confirmed. Minor.**

### import_history: empty-rows month accepted

```sql
elsif exists (select 1 from jsonb_array_elements(p_bundle -> 'months') m
              where jsonb_typeof(m -> 'rows') is distinct from 'array') then
  v_bad := 'Every month needs a list of rows';
```

This catches a missing or non-array `rows` key but not `rows: []`. A direct `postgres`-role call with an empty month would close it with no entries and no member statements, leaving the group's closing balance wrong and the cycle partially unusable. The JS layer prevents this, but the SQL function is the canonical validator. Add:

```sql
or jsonb_array_length(m -> 'rows') = 0
```

to the condition. **Confirmed. Minor.**

### workbook_term_differs: overly broad upper bound

```sql
when e.principal_left > 0 and abs(d.difference) <= e.principal_left then 'workbook_term_differs'
```

For a member who borrowed K8,000 and still owes K7,000, any minimum difference up to K7,000 gets this code. That covers almost any realistic discrepancy for any active borrower. The `1350` migration tightened this from the unconditional `e.principal_left > 0` in `1300`, but the upper bound is still the full outstanding balance rather than a monthly instalment amount. Classify it as a known approximation in a comment, or tighten to one instalment's worth. **Confirmed. Minor.**
